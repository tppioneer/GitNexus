# GitNexus 产品介绍

## 背景：为什么需要知识图谱，为什么做 GitNexus

传统代码搜索（如 grep）只能做文本匹配——搜索函数名返回所有出现该字符串的地方，包括注释、字符串常量、相似命名等大量噪音。它完全无法回答"谁调用了这个函数""改了这里会影响哪些模块"这类结构化问题。

代码知识图谱将函数、类、模块及其之间的调用、继承、数据流关系建模为图结构。这让 AI 编程助手不仅能"读到"代码，更能"理解"代码所处的上下文——调用链、影响范围、执行流程一目了然。

GitNexus 正是为此而生：它自动分析代码仓库，构建覆盖符号、关系和执行流的知识图谱，并通过 MCP 协议暴露为结构化的代码智能服务。无论是探索陌生项目、调试疑难 Bug、还是评估改动影响范围，GitNexus 让 AI 助手能够像资深工程师一样理解代码，而非仅靠文本匹配。

## 部署架构：一次构建，团队共享

GitNexus 支持两种部署模式，其中远程服务模式是区别于传统代码分析工具的核心差异：

### 本地模式（单开发者）

开发者在本机运行 `gitnexus analyze`，索引存储于本地 `.gitnexus/` 目录，仅自己使用。适合个人项目和快速实验。

### 远程 MCP 服务模式（团队共享）

```
                    ┌───────────┐
                    │  CI/CD    │
                    │  Pipeline │
                    └─────┬─────┘
                          │ 每次 push develop/main
                          │ 自动触发 gitnexus analyze
                          ▼
              ┌─────────────────────┐
              │   GitNexus Server   │
              │   ┌───────────────┐ │
              │   │  知识图谱索引   │ │
              │   │  · 符号        │ │
              │   │  · 调用关系    │ │
              │   │  · 执行流      │ │
              │   └───────────────┘ │
              │   MCP 协议接口      │
              └──────────┬──────────┘
                         │
          ┌──────────────┼──────────────┐
          │              │              │
          ▼              ▼              ▼
    ┌──────────┐  ┌──────────┐  ┌──────────┐
    │ 开发 A   │  │ 开发 B   │  │ 开发 C   │
    │ Claude   │  │ Claude   │  │ Claude   │
    │ Code     │  │ Code     │  │ Code     │
    └──────────┘  └──────────┘  └──────────┘

    ✅ 每个 AI 助手通过 MCP 协议直接访问同一份知识图谱
    ✅ 无需本地索引，不需要本地源码
    ✅ 新人上手零等待
```

**核心价值——一次构建，全团队共享：**

| 对比维度 | 传统 IDE/本地工具 | GitNexus 远程 MCP 模式 |
|---------|-----------------|---------------------|
| 索引构建 | 每个开发者本地跑一次 | 服务端 CI 构建一次，全员复用 |
| 新人成本 | 拉代码 + 装工具 + 等索引（数十分钟） | MCP 直连，零等待 |
| 代码版本一致性 | 各人本地分支不同，索引各异 | 统一反映基准分支（develop/main），团队共享一份"代码地图" |
| 硬件要求 | 大型仓库索引耗费本地 CPU/内存 | 服务端承担，开发者机器零负载 |
| 跨仓库理解 | 需要本地 clone 所有关联仓库 | 服务端索引多个仓库，`query`/`context` 自动跨仓库追踪 |
| AI 助手的代码理解 | 只能靠 Read 工具逐文件读代码 | 知识图谱直接提供结构化的符号关系和执行流 |

> **关键约束（远程模式）**：开发者本地没有源代码，或本地代码与索引版本不一致。AI 助手不能依赖 `Read` 源文件——知识图谱本身（`context`、`trace`、`process`、`query`）就是唯一的信息来源。这就是为什么 GitNexus 的知识图谱需要足够丰富：它不仅告诉你"符号在哪"，更告诉你符号之间的关系和在整个系统架构中的位置。

## GitNexus Skills：探索与调试

### gitnexus-exploring —— 代码探索

当你需要理解陌生代码、追踪架构、搞懂"XX 是怎么实现的"时，使用此 Skill。它提供了一套结构化的探索工作流：

1. **概览全局**：通过 `gitnexus://repo/{name}/context` 快速了解代码库规模、符号数、执行流数量和索引新鲜度
2. **语义搜索**：用 `query({search_query: "概念"})` 搜索与某个功能概念相关的执行流——比如搜索"支付处理"直接返回 CheckoutFlow、RefundFlow 等，而非简单的文本匹配结果
3. **全景视图**：用 `context({name: "函数名"})` 查看任意符号的 360° 关系——谁调用了它、它调用了谁、参与了哪些端到端流程
4. **最短路径**：用 `trace({from: "A", to: "B"})` 一键找出两个符号之间的调用链，无需手动逐跳拼接

优势：grep 搜"payment"可能返回 200+ 个文件的所有出现位置，而 `query` 返回的是按执行流分组的语义结果，`context` 直接给出调用关系图——信息密度和精准度远超传统文本搜索。

### gitnexus-debugging —— 调试诊断

当你排查 Bug、追踪错误来源、调查"为什么 X 会失败"时，使用此 Skill。它提供了从症状到根因的完整调试链路：

1. **从症状出发**：`query({search_query: "错误信息"})` 找到与该错误相关的所有执行流和符号
2. **锁定嫌疑人**：在返回的符号中锁定可疑函数
3. **追踪调用链**：`context` 查看该函数的上下游调用关系，`trace` 快速追踪"两个符号之间怎么到"的最短路径
4. **确认根因**：通过 GitNexus 返回的文件路径，精确定位源文件，阅读实现细节确认根因

典型场景：支付接口间歇性 500 → `query` 搜索"payment error"定位到 validatePayment → `context` 发现它调用了 fetchRates（外部 API）→ `trace` 确认调用链 → Read 源文件确认 fetchRates 没有配置超时。

## Skills 如何使用 MCP 能力

GitNexus 的 Skills 本质上是对 MCP 工具链的**编排指南**——它们告诉 AI 助手在什么场景下、以什么顺序、调用哪些 MCP 工具。以下是两个核心 Skill 如何串联 MCP 能力的详细说明。

### gitnexus-exploring 的 MCP 调用链

探索陌生代码时，AI 助手按照 Skill 指引，逐步调用 MCP 工具构建认知地图：

```
第一层：发现与概览
┌─────────────────────────────────────────────────────────┐
│ list_repos({})                     MCP Tool             │
│   → 返回已索引仓库列表                                   │
│ READ gitnexus://repo/{name}/context  MCP Resource        │
│   → 返回符号数、执行流数、索引时间                       │
│ READ gitnexus://repo/{name}/clusters  MCP Resource       │
│   → 返回功能模块分组（社区检测结果）                      │
│                                                         │
│ 作用：建立"这个项目有多大、有哪些模块"的全局认知          │
└─────────────────────────────────────────────────────────┘
                          ↓
第二层：概念定位
┌─────────────────────────────────────────────────────────┐
│ query({search_query: "认证流程", repo: "my-app"})       │
│   → Processes: LoginFlow, TokenRefresh, LogoutFlow      │
│   → Symbols grouped by flow with file locations          │
│                                                         │
│ 作用：从"我想理解认证"的自然语言 → 精确定位相关代码结构  │
│ grep做不到：搜"认证"返回几千行，而query按执行流分组返回   │
└─────────────────────────────────────────────────────────┘
                          ↓
第三层：符号深潜
┌─────────────────────────────────────────────────────────┐
│ context({name: "validateUser", repo: "my-app"})         │
│   → Incoming calls: loginHandler, apiMiddleware          │
│   → Outgoing calls: checkToken, getUserById              │
│   → Processes: LoginFlow (step 2/5)                      │
│                                                         │
│ 作用：以validateUser为中心，看它的上下游调用和所属流程    │
│ grep做不到：只知道哪里写了"validateUser"，不知道调用关系   │
└─────────────────────────────────────────────────────────┘
                          ↓
第四层：路径追踪
┌─────────────────────────────────────────────────────────┐
│ trace({from: "loginHandler", to: "getUserById"})        │
│   → hops: loginHandler → validateUser → getUserById     │
│   → edges: CALLS (1.0), CALLS (0.95)                    │
│                                                         │
│ 作用：一键找出A到B的完整调用链，含置信度                  │
│ grep做不到：完全无法回答"怎么从A到B"                     │
└─────────────────────────────────────────────────────────┘
```

每一步 MCP 调用都是**结构化的图查询**，返回的不是文本片段而是带关系标注的符号信息。AI 助手拿到的不再是"一个字符串出现了几次"，而是"这个函数在整个系统中的位置和关系网"。

### gitnexus-debugging 的 MCP 调用链

调试时，AI 助手从症状出发，反向推导根因：

```
第一步：从症状定位代码区域
┌─────────────────────────────────────────────────────────┐
│ query({search_query: "NullPointerException checkout"})  │
│   → Processes: CheckoutFlow, ErrorHandler               │
│   → Symbols: processCheckout, validateCart, CartService │
│                                                         │
│ 作用：错误信息 → 相关执行流和可疑符号                     │
│ grep做不到：搜异常堆栈只能找到throw那一行，看不到完整流程  │
└─────────────────────────────────────────────────────────┘
                          ↓
第二步：锁定嫌疑人
┌─────────────────────────────────────────────────────────┐
│ context({name: "validateCart"})                         │
│   → Incoming: processCheckout                           │
│   → Outgoing: fetchInventory (external API!)             │
│   → Outgoing: calculateTotal, applyDiscount              │
│                                                         │
│ 作用：看validateCart的所有被调用者，找外部依赖/副作用     │
│ grep做不到：无法区分"谁调用了它"和"它调用了谁"           │
└─────────────────────────────────────────────────────────┘
                          ↓
第三步：追踪执行流
┌─────────────────────────────────────────────────────────┐
│ READ gitnexus://repo/my-app/process/CheckoutFlow        │
│   → Step 1: receiveOrder                                │
│   → Step 2: validateCart  ← 问题在这                    │
│   → Step 3: processPayment                              │
│   → Step 4: sendConfirmation                            │
│                                                         │
│ 作用：看validateCart在整个业务流程中的位置和上下文        │
│ grep做不到：完全不知道"执行流"这个概念                   │
└─────────────────────────────────────────────────────────┘
                          ↓
第四步：确认根因（可选自定义查询）
┌─────────────────────────────────────────────────────────┐
│ cypher({statement:                                       │
│   "MATCH (f:Function {name:'validateCart'})              │
│    -[:CodeRelation*1..3]->(caller)                       │
│    RETURN caller.name"})                                 │
│   → 返回validateCart 3跳内所有下游调用                   │
│                                                         │
│ trace({from: "processCheckout", to: "APIException"})    │
│   → 无完整路径，最远可达 fetchInventory（外部API边界）    │
│                                                         │
│ 作用：灵活的自定义查询，或确认调用链断裂点                 │
│ grep做不到：完全没有图查询能力                            │
└─────────────────────────────────────────────────────────┘
                          ↓
第五步：源文件确认
┌─────────────────────────────────────────────────────────┐
│ Read src/cart/validator.ts             普通文件读取       │
│   → fetchInventory调用处没有 try-catch                   │
│   → 没有超时配置                                        │
│   → 根因确认：外部API调用无容错处理                      │
│                                                         │
│ 作用：在知识图谱提供精确定位后，读源文件确认实现细节       │
│ 关键：不是从grep开始漫无目的地翻文件，                     │
│       而是MCP工具精确定位到行，再读文件验证                │
└─────────────────────────────────────────────────────────┘
```

### 两者协作的完整模式

在实际使用中，exploring 和 debugging 不是孤立的：

```
       exploring                          debugging
    （正向探索）                        （反向排查）
         │                                   │
         │  "这个系统怎么设计的？"             │  "为什么这里出错了？"
         │                                   │
         ▼                                   ▼
   query(概念) ────────────┐        query(错误信息) ────────────┐
         │                 │              │                      │
         ▼                 │              ▼                      │
   context(符号)           │        context(嫌疑人)               │
         │                 │              │                      │
         ▼                 │              ▼                      │
   READ process            │        READ process                 │
         │                 │              │                      │
         ▼                 │              ▼                      │
   trace(A→B)              │        cypher(自定义查询)            │
         │                 │              │                      │
         └─────────┬───────┘              └──────────┬───────────┘
                   │                                 │
                   └────────────┬────────────────────┘
                                ▼
                         Read 源文件确认
                    （精确定位，而非盲目搜索）
```

**关键差异**：

| 对比维度 | grep / 文本搜索 | GitNexus MCP |
|---------|----------------|-------------|
| 搜索方式 | 字符串匹配 | 图遍历 + BM25 + 语义搜索 |
| 返回内容 | 匹配的代码行 | 符号 + 关系 + 执行流分组 |
| "谁调用了它" | 无法回答 | `context` 一步获取 |
| "改了影响谁" | 无法回答 | `impact` 上游追溯 + 风险评级 |
| "A怎么到B" | 无法回答 | `trace` 最短调用路径 |
| "涉及哪些流程" | 手动拼凑 | `query` 直接按执行流分组 |
| 噪音 | 注释、字符串、子串 | 精确到符号级别的结构化结果 |

### MCP 服务提供的能力

GitNexus 通过 MCP（Model Context Protocol）协议，为 Claude Code 等 AI 编程助手提供以下结构化代码智能工具：

| 工具 | 能力 | 典型用途 |
|------|------|---------|
| `query` | 混合 BM25 + 语义搜索，返回与概念相关的执行流和符号 | "认证逻辑在哪" |
| `context` | 符号 360° 全景视图：调用者、被调用者、参与的执行流 | "这个函数被谁调用了" |
| `impact` | 向上游追溯改动影响范围，评估风险等级 | "改了它会影响哪些地方" |
| `trace` | 两个符号之间的最短调用路径 | "A 怎么到达 B" |
| `detect_changes` | 对比改动前后，列出受影响的符号和执行流 | 提交前确认改动范围 |
| `cypher` | 自定义图查询语句，支持灵活的调用链分析 | "找出所有调用外部 API 的函数" |
| `explain` | 安全分析：列出污点数据流（source → sink） | "这段代码有注入风险吗" |
| `rename` | 基于调用图的精确重命名（非 find-replace） | 安全重构符号名称 |

**核心理念**：不只是在代码文本中搜索关键词，而是在代码的**关系结构**中思考和导航。知识图谱让 AI 助手对代码的理解，从"字面匹配"升级为"关系推理"。
